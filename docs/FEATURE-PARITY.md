# Feature parity: keeping the API and MCP in step with ElectroHire

The API and the MCP server are public contracts. People build agents against
them. If the website gains a feature and the agent surfaces quietly stay
behind — or a feature disappears from the platform while its endpoint keeps
answering — agent builders find out the hard way, from broken workflows
instead of from us.

So parity is a rule of this repository, not a cleanup pass:

> **Every feature added, changed, or removed in the ElectroHire website or
> platform gets an API/MCP parity assessment in the same change** — the same
> pull request, the same release — never a later "we should expose that too"
> ticket that may or may not happen.

## Parity states

Every surface (each API route, each MCP tool) carries exactly one parity
state in the manifest:

| State | Meaning |
|---|---|
| `exposed` | The surface exists and is the agent-facing form of a current platform feature (or a platform endpoint in its own right, like health and the OpenAPI document). |
| `not-exposed` | Deliberately **not** offered to agents. The reason is recorded in the manifest — typically because the feature is admin-only, internal, or unsafe for agents to drive. This is a decision, not an omission. |
| `pending` | The feature exists (or is planned) and should be exposed, but the API route or MCP tool is not built yet. The manifest entry names the spec or task that will expose it, so "pending" is a tracked commitment, not a shrug. |

A surface with an empty or "not yet classified" reason is unfinished work:
classify it in the same change that introduces it.

## The manifest is the source of truth

[`parity-manifest.json`](../parity-manifest.json) at the repository root is
the checked-in record of every API route and MCP tool and its parity state.
It is generated by [`tools/parity-manifest.mjs`](../tools/parity-manifest.mjs):

```bash
node tools/parity-manifest.mjs        # or: pnpm parity
```

The generator scans `apps/api` for route registrations and `apps/mcp` for
registered tool names, then rewrites the manifest. The split of ownership:

- **The generator owns discovery** — names, kinds, and source files always
  match the code.
- **Humans own classification** — `state` and `reason` written in the
  manifest survive regeneration. The generator never overwrites a human's
  parity decision; a newly discovered surface enters as `pending` /
  "not yet classified" until a human classifies it.

CI runs the generator on every push and pull request and **fails the build
if the committed manifest differs from what the code generates**. A stale
manifest is a failed check, the same as a type error.

## Adding or changing a feature

1. Build the feature (website, platform, or agent surface).
2. Decide the parity outcome in the same change:
   - expose it → add/adjust the API route and/or MCP tool, set `exposed`;
   - keep it from agents → set `not-exposed` with the reason;
   - expose it later → set `pending` with the spec/task that will do it.
3. Run the generator and commit the regenerated manifest with your change.
4. Note the parity outcome in the CHANGELOG entry for the change.

## Removing a feature

Removals deprecate before they disappear:

1. **Deprecate first.** Mark the route or tool deprecated (in its schema
   description and the CHANGELOG), flip its manifest state with a reason
   naming the removal, and keep it working for a notice period — one minor
   release of the affected component, minimum — unless the surface is a
   security risk, which is the one reason to remove immediately, recorded
   as such.
2. **Then remove.** When the endpoint or tool leaves the code, the
   generator moves its manifest entry to `missingFromCode` rather than
   silently dropping it, so the removal stays visible in review. Delete the
   `missingFromCode` entry in the change that completes the deprecation.
3. Versioned surfaces (`/v1`, tool versions) follow the versioning policy in
   [`docs/architecture.md`](architecture.md#versioning-policy): a breaking
   removal is a new version alongside the old during the notice period,
   never a silent edit to a live contract.

## Who owns it

Whoever changes a feature owns its parity line. Reviewers check the manifest
diff the way they check a schema diff: a feature change with no parity
assessment — no state, no reason, no pending pointer — is not ready to merge.

## The standing rule, and the gate that enforces it (2026-10-26)

The owner made the parity rule absolute on 2026-10-26:

> **No system change ships without its MCP + skills updates in the same
> change.** If a platform change alters anything an agent can see or do,
> the MCP tools, the served OpenAPI, the skill packages, and the
> connector guides are updated in that same change — or the change does
> not ship. This is enforced by CI, not by memory.

The enforcement is the **coverage gate**, `tools/check-coverage.mjs`,
which runs as a blocking CI job in this repo. It enumerates the served
OpenAPI operations (from the API code), the MCP tools (from the MCP
code), and every tool/endpoint reference in the skills, connector
guides, docs, app READMEs, and the Python SDK, and it **fails** when
they diverge from `tools/coverage-map.json`:

- an operation with no MCP tool and no recorded reason it has none;
- a tool no operation maps to and no recorded reason;
- a skill, guide, doc, or SDK reference to a tool or endpoint that
  does not exist;
- a tool or operation that shipped but no doc surface mentions;
- the API-key scope catalog and the OAuth offered scopes disagreeing.

The website repo carries the mirror-image gate
(`scripts/check-agent-coverage.mjs` against
`specs/004-api-mcp/agent-surface-inventory.json`): every platform
capability there carries a disposition — exposed (naming the operation,
tool, and scope), not exposed (with the reason), or pending (with the
pointer) — and its CI fails the same way. The two files name the same
operations and tools; changing one side without the other is exactly
the divergence both gates exist to catch.
